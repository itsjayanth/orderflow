# Orderflow — Broadcast/Campaign Messaging Implementation Plan

Continues `IMPLEMENTATION_PLAN.md` past its Phase 11 (and the Website Link addendum). There is no separate `docs/broadcast-messaging-feature.md` proposal doc for this feature — this plan **is** the spec, built directly from `docs/product-roadmap.md`'s Phase 2 "WhatsApp Broadcast Campaign Engine" backlog ticket, the campaign/retention framing in `docs/product-vision.md`, and a small set of settled architectural decisions (messaging-tier field placement, media-header scope, opt-out compliance) made while reading the current codebase rather than left for a later doc to resolve. Where this plan cuts scope relative to what the roadmap ticket's own prose implies (segmentation, retry policy, analytics), that's called out inline and summarized in "Assumptions made in absence of a proposal doc" below — same convention `IMPLEMENTATION_PLAN.md`'s own phases use for deviations from `MULTI_VERTICAL_PLAN.md`/`VERTICAL_TOGGLE_PLAN.md`.

Two adjacent Phase 2 backlog tickets are explicitly **not** built here, on purpose: the **Customer Segmentation Engine** (a separate, not-yet-scheduled ticket the campaign ticket's "target segment" language leans on) and the **Email Campaign Channel** (P2, a second channel layered onto whatever `Campaign` model this plan produces). This plan's `Campaign`/`AudienceFilter` shape is deliberately designed so both slot in later without a rewrite — see Phase 14's audience-targeting section and the Assumptions list. The **Automated Reorder/Refill Reminders** and **Lost Customer Win-back Campaigns** tickets that follow this one on the roadmap are also out of scope to build, but both name this engine as their delivery mechanism, so Phase 14 exposes a same-process `create_campaign()` domain function (not just an HTTP endpoint) as the interface those future scheduled jobs will call — the same "module calls module directly, no internal HTTP layer" convention `onboarding/domain/onboarding_service.py`'s `catalog_ready` gate already uses against Catalog/Appointment Service.

Every phase follows `IMPLEMENTATION_PLAN.md`'s own stated shape: 1. Migration 2. Domain 3. Adapters 4. API 5. Backend tests 6. Frontend 7. Frontend tests, each ending in a **Definition of done** — the concrete thing you can curl or click through. Phases are ordered so each is independently demoable and depends only on earlier phases: opt-out/compliance foundation (a hard platform requirement, so it goes first, not last) → template creation/submission/approval-webhook → the campaign send engine itself (audience targeting, scheduling, tier-ceiling enforcement, reusing the existing WhatsApp send path) → the dashboard UI on top of it → video/document template headers, deliberately last because they're a small additive change to Phase 13's media adapter, not new plumbing.

## Phase 12 — Marketing opt-out & compliance foundation

WhatsApp Business Platform policy requires honoring STOP/opt-out for marketing-category messages, and nothing in this codebase does that today — confirmed by reading both places it would live: `conversation/domain/intents.py`'s keyword table has no STOP/unsubscribe entry, and `customers/domain/models.py` has no opt-out field of any kind. Every later phase in this plan sends real MARKETING-category templates to real customers, so this is a hard prerequisite, not later polish, and goes first rather than being bolted on after Phase 14 already has a send path live. The highest-risk piece is precision, not novelty: the opt-out check has to intercept before any campaign audience is resolved (so an already-in-flight send run stops including someone who just opted out), and it must apply *only* to marketing sends — a customer who opts out of campaigns must still receive their order-ready/appointment-confirmed transactional notifications, since Meta treats those as a different message category entirely and this codebase's existing `NotificationChannel` path has no reason to change.

**Backend**
- Migration: `customers` gains `marketing_opt_out: bool` (default `False`) and `marketing_opt_out_at: datetime | None`.
- `customers/domain/models.py`: add the two fields above to `Customer`.
- `conversation/domain/intents.py`: new `Intent.OPT_OUT` / `Intent.OPT_IN`. Unlike every existing entry in `_TEXT_KEYWORDS` (which matches on `keyword in lowered`, a substring check), these two are matched on an **exact**, stripped, case-insensitive equality against `{"stop", "unsubscribe"}` / `{"start", "subscribe"}` — a substring match would misfire on ordinary customer text like "please stop shipping it late" or "what's the status" (contains "stop"? no, but "unsubscribe" and "start" are plausible substrings of longer sentences too), and Meta's own guidance treats STOP as a dedicated command, not a phrase fragment. Checked ahead of every other keyword in `classify()`, since an opt-out has to win even against a message that also happens to contain "order" or "book". Reasoned as a deviation from the file's existing substring-matching convention, not an oversight — flagged inline in `intents.py` itself.
- `conversation/domain/handler.py`: `_reply_for_intent` gains an `Intent.OPT_OUT` / `Intent.OPT_IN` branch (same shape as the existing `Intent.VISIT_WEBSITE` branch) — updates `Customer.marketing_opt_out`/`marketing_opt_out_at` via a new repository method, then replies with a short confirmation ("You won't receive marketing messages from {business_name} anymore. Reply START to resubscribe." / "You're resubscribed to updates from {business_name}."). Placed as its own top-of-`_reply_for_intent` branch, ahead of the vertical-gated intents, so it fires regardless of which vertical(s) a merchant has enabled.
- `customers/adapters/repository.py`: `CustomerRepository.set_marketing_opt_out(tenant, customer_id, *, opted_out: bool) -> Customer`.
- `customers/api/router.py`: extend the existing `GET /api/v1/customers/{id}` response schema with `marketing_opt_out`/`marketing_opt_out_at` (read-only — per `ARCHITECTURE.md`'s existing "writes only happen from the WhatsApp ordering flow" rule for this module, staff cannot toggle a customer's opt-out status from the dashboard; only the customer's own STOP/START message can, deliberately, so a merchant can't just flip someone back on against their wishes).
- Tests: exact-match classification for STOP/START (and non-match for "please stop the noise" style substrings, proving the deviation from the file's usual substring convention is real and tested); handler test that OPT_OUT flips the flag and sends the confirmation; OPT_IN flips it back; a regression test asserting `notifications/adapters/whatsapp_channel.py`'s existing order-lifecycle sends are unaffected by `marketing_opt_out=True` (proving the transactional/marketing category split holds structurally, not just by convention).

**Frontend**
- `frontend/src/features/customers/CustomersPage.tsx`: add a small "Opted out" badge next to a customer's row/detail when `marketing_opt_out` is true — read-only, matching Phase 3's existing read-only Customers page.

**Definition of done**: simulate an inbound "STOP" WhatsApp webhook from a seeded customer; `GET /api/v1/customers/{id}` shows `marketing_opt_out: true`; the dashboard Customers page shows the "Opted out" badge for that customer; simulate "START" and confirm it flips back; separately, advance a seeded order to `ready` for that same (still opted-out, for the STOP-only half of the test) customer and confirm the existing WhatsApp order-ready notification still sends — proving transactional sends are untouched by this feature.

## Phase 13 — WhatsApp template creation, submission & Meta approval webhook

Template creation and submission is real from the start here, not a "merchant pastes a template name from Meta Business Manager" placeholder — because it doesn't need to be a placeholder. `backend/src/onboarding/domain/embedded_signup.py`'s `_verify_waba_scope` already requests and verifies the `whatsapp_business_management` granular scope covers the connected WABA before any token is persisted, and `shared/config.py`'s `meta_app_id` docstring records that this Meta App is already **App Review-approved for `whatsapp_business_management`/`whatsapp_business_messaging`** in production, not just requested. The resulting long-lived token sits encrypted on `WhatsAppBusinessAccount.access_token_encrypted` today, exercised live by every outbound send this codebase already makes. So `POST /{waba_id}/message_templates` using that same stored token is a straightforward new call against an already-proven credential path, not a call gated on some missing prerequisite — this phase absorbs what a naive plan might push to a later "unblock Meta access" phase, and it's worth saying so explicitly since it changes what "Phase 13" would otherwise need to be. No blocking prerequisite was found for this phase.

The highest-risk piece is the approval webhook, not the creation call: Meta's template review is async (minutes to a day), so `meta_approval_status` has to update itself from a webhook, not a merchant hitting refresh. `conversation/api/router.py`'s existing `receive_webhook` and `conversation/domain/webhook_parser.py`'s `parse_inbound_messages` today only read `entry[].changes[].value.messages` — any other `field` value (Meta multiplexes several event types onto the same webhook URL, distinguished by `changes[].field`) is silently ignored. Rather than a separate route (Meta's subscription is app-level and already covers this field once subscribed, and the webhook body itself carries both message and status-update changes interleaved), this phase adds a second parse function read off the same inbound payload.

**Backend**
- New module `backend/src/campaigns/{domain,adapters,api}`, same hexagonal shape as every other module.
- Migration: `message_templates` table.
- `campaigns/domain/models.py`: `MessageTemplate` — `template_id` (uuid pk), `merchant_id` (FK), `name` (String(512), Meta requires lowercase snake_case, normalized on save), `category` (`MARKETING` | `UTILITY`), `language_code` (String(16), default `"en_US"`), `header_type` (`NONE` | `TEXT` | `IMAGE` — `VIDEO`/`DOCUMENT` added in Phase 16), `header_text` (nullable String(60), TEXT headers only), `header_media_handle` (nullable String — Meta's opaque upload handle from the Resumable Upload API, IMAGE headers only), `body_text` (Text, `{{1}}`-style placeholders), `body_variable_count` (int, derived and stored at save time so later validation doesn't have to re-parse `body_text`), `footer_text` (nullable String(60)), `buttons` (JSON list of `{type: "QUICK_REPLY"|"URL", text, url?}` — the `URL` type mirrors the existing CTA-URL button pattern `conversation/adapters/whatsapp_client.py`'s `send_cta_url_button` already uses for the website-link feature, just submitted as part of a template instead of sent ad hoc), `meta_template_id` (nullable String), `meta_approval_status` (`pending` | `approved` | `rejected` | `paused` | `disabled`, default `pending`), `meta_rejection_reason` (nullable Text), `created_at`/`updated_at`. This is a deliberately new model, not an extension of `notifications/domain/models.py`'s existing `NotificationTemplate` — that model holds merchant-authored freeform `{{var}}` text with no Meta template id, category, or approval concept at all (it's rendered locally and sent via plain `send_text`/`send_template_message` for the one reminder case that needs it); a MARKETING template needs real Meta submission and approval tracking that `NotificationTemplate` was never built for, so reusing it would mean bolting an unrelated concept onto an existing one rather than adding a genuinely new one.
- `campaigns/domain/template_validation.py`: pure validation, no I/O — `{{1}}`, `{{2}}`, ... must be sequential with no gaps starting at 1; `category` is one of the two enum values; header/body/footer length caps per Meta's documented limits (header text ≤60 chars, body ≤1024 chars, footer ≤60 chars); raises a typed `InvalidTemplateError` the API layer maps to 422.
- `campaigns/adapters/media_upload.py`: `upload_header_image(waba: WhatsAppBusinessAccount, image_bytes: bytes, content_type: str) -> str` — calls Meta's Resumable Upload API (`POST /{app_id}/uploads` to start a session, then `POST /{upload_session_id}` with the bytes) to obtain a `header_handle` string, which becomes the HEADER component's `example.header_handle` at template-creation time. Named and shaped deliberately as the seam Phase 16 generalizes: the underlying Resumable Upload call is identical for image/video/document, so this function's signature (raw bytes + content type in, an opaque handle string out) doesn't hardcode an image-only assumption anywhere in its call site or return type — only its internal `_MAX_SIZE_BYTES`/`_ALLOWED_CONTENT_TYPES` constants are image-specific, which is exactly what Phase 16 changes.
- `campaigns/adapters/template_gateway.py`: `MetaTemplateGateway.create_template(waba, template: MessageTemplate) -> tuple[str, str]` (returns `(meta_template_id, initial_status)`) calling `POST /{waba_id}/message_templates` with the merchant's decrypted token — same `WhatsAppBusinessAccountRepository(session).get(tenant)` + `shared/encryption.decrypt()` pattern every other outbound-Meta call in this codebase already follows (`notifications/adapters/whatsapp_channel.py`, `flows/domain/setup.py`); `delete_template(waba, meta_template_id)` for the delete endpoint below.
- `conversation/domain/webhook_parser.py`: new `parse_template_status_updates(payload: dict) -> list[TemplateStatusUpdate]` (`TemplateStatusUpdate`: `meta_template_id`, `status`, `reason: str | None`) — reads `entry[].changes[]` where `field == "message_template_status_update"`, mirroring `parse_inbound_messages`'s existing "walk entry/changes, skip anything not shaped like what I'm looking for" structure exactly, just keyed off `field` instead of the presence of a `messages` list.
- `conversation/api/router.py`: `receive_webhook` calls both parsers against the same already-parsed payload (`parse_inbound_messages` for messages, `parse_template_status_updates` for template events) — no new route, since Meta delivers both change types to the one subscribed webhook URL. Each `TemplateStatusUpdate` is applied via `campaigns/domain/template_status.py`'s `apply_template_status_update(session, update)` → `MessageTemplateRepository.update_approval_status(meta_template_id, status, reason)` (a cross-tenant lookup by `meta_template_id`, same "resolve tenant from the Meta-side id, not a client-supplied one" pattern `WhatsAppBusinessAccountRepository.get_by_phone_number_id`/`get_by_flow_id` already establish).
- `campaigns/adapters/repository.py`: `MessageTemplateRepository` — tenant-scoped CRUD, plus the cross-tenant `get_by_meta_template_id` the webhook handler needs.
- `campaigns/api/router.py`: `POST /api/v1/campaigns/templates` (validates via `template_validation.py`, uploads any header image via `media_upload.py`, calls `MetaTemplateGateway.create_template`, persists with `meta_approval_status="pending"`), `GET /api/v1/campaigns/templates` (list), `GET /api/v1/campaigns/templates/{id}`, `DELETE /api/v1/campaigns/templates/{id}` (deletes at Meta first, then locally, mirroring `flows/domain/setup.py`'s "durable state matches Meta's, in that order" discipline). Editing is intentionally **not** supported once `meta_template_id` is set — Meta requires deleting and resubmitting a template to change its approved content, so `PUT` only exists implicitly via delete+recreate from the frontend, not a template-mutation endpoint (flagged in Assumptions below).
- Tests: template validation (sequential variable numbering including a gap/duplicate case, length caps, category enum); `MetaTemplateGateway` request-shape test against a fake `httpx` transport (payload structure, `Authorization` header, header-handle wiring); `parse_template_status_updates` (approved/rejected/paused entries, a `reason` field present only on rejection, an unrelated `field` value silently ignored); end-to-end router test: create a template (mocked Meta response) → `pending` → simulate the status-update webhook → `approved`, asserting no polling call was made.

**Frontend**
- New `frontend/src/features/campaigns/` feature directory: `useTemplates.ts` (list/create/delete hooks), `TemplateForm.tsx` (category select, header-type select [None/Text/Image], body textarea with `{{1}}` variables highlighted and a live variable-count readout, footer input, a buttons editor for quick-reply/URL buttons — mirrors `CatalogPage.tsx`'s existing add-item form conventions: RHF + Zod, shadcn `Select`/`Input`/`Textarea`), `TemplatesPage.tsx` (table of templates with an approval-status badge — pending/approved/rejected/paused/disabled — and a rejection-reason tooltip when present; "New template" opens `TemplateForm` in a dialog, same pattern `CatalogPage.tsx` uses for "Add item").
- New `/campaigns/templates` route + a "Campaigns" nav section in `shared/components/Layout.tsx`, shown unconditionally (not gated by `restaurant_enabled`/`appointment_enabled` the way Catalog/Services are — campaigns aren't vertical-specific; flagged as an assumption below).
- Tests: form validation (variable-count mismatch between body and declared count is caught client-side before submit); status badge rendering per `meta_approval_status` value, including the rejection-reason tooltip.

**Definition of done**: from the dashboard, create a MARKETING template with a `{{1}}` body variable and an image header, submit it — `GET /api/v1/campaigns/templates/{id}` shows `meta_approval_status: "pending"` and a real `meta_template_id`; simulate an inbound `message_template_status_update` webhook reporting `APPROVED` — the same row flips to `approved` with zero polling calls made, and the dashboard reflects it on next load.

## Phase 14 — Campaign entity, audience targeting, and scheduled send with tier-ceiling enforcement

This is the core of the roadmap ticket: turning an approved template (Phase 13) and a target audience into an actual batch of outbound WhatsApp sends, on a schedule, without tripping Meta's per-number throughput or messaging-tier limits. It explicitly reuses `conversation/adapters/whatsapp_client.py`'s send path and per-merchant token handling, per the ticket's own acceptance criteria, and its scheduled-send job follows `shared/scheduler.py`'s existing abandoned-order-sweep/appointment-reminder pattern (a plain interval job, no queue infrastructure, per `TECH_STACK.md`'s explicit "APScheduler, not Celery+Redis" decision). The highest-risk piece is getting the messaging-tier ceiling and its overflow behavior right under a status model (`draft`/`scheduled`/`sending`/`completed`/`failed`) that has no "partially sent, paused for today" state of its own — the send job has to make that distinction hold up through `CampaignRecipient` rows instead.

**Messaging tier — where it lives and why.** Meta assigns messaging tiers ("Tier 1 Limited Access: 250/24h", up through unlimited) per phone number, not per business — so the natural home is `WhatsAppBusinessAccount` (which already owns `phone_number_id`/`connection_status`), not `Merchant` and not a new per-merchant table, even though this codebase's single-outlet-per-merchant assumption means the two are practically 1:1 today. New field: `WhatsAppBusinessAccount.messaging_tier_daily_limit: int` (default `250`, matching Meta's default "Limited Access" tier), admin-settable exactly like `Settings.abandoned_order_timeout_minutes` is today — a real editable field, not a hardcoded constant, surfaced on the Settings page (below) rather than only settable via env var, since it varies per merchant as their WABA graduates tiers, unlike `abandoned_order_timeout_minutes` which is genuinely platform-wide.

**Backend**
- Migration: `whatsapp_business_accounts` gains `messaging_tier_daily_limit` (int, `server_default '250'`); new `campaigns`, `campaign_recipients` tables.
- `campaigns/domain/models.py` (extends Phase 13's module): `Campaign` — `campaign_id`, `merchant_id` (FK), `name`, `template_id` (FK to `MessageTemplate`), `audience_filter` (JSON, see below), `scheduled_at` (nullable `datetime` — `None` means send-now, picked up on the scheduler's very next tick), `status` (`draft` | `scheduled` | `sending` | `completed` | `failed`), `created_by` (String — either a `staff_user_id` UUID string or a future `"system:<job-name>"` sentinel, mirroring `OrderStatusEvent.changed_by`'s existing human-or-system convention exactly, so a not-yet-built Automated Reorder Reminder job can stamp its own campaigns distinctly from staff-created ones without a schema change), `created_at`/`updated_at`/`completed_at` (nullable).
- `CampaignRecipient` — append-only per-recipient ledger, same shape as `PaymentEvent`/`OrderStatusEvent`/`inventory-stock-management-feature.md`'s proposed `StockMovement`: `recipient_id`, `campaign_id` (FK), `customer_id` (FK), `status` (`pending` | `sent` | `failed` | `skipped_opted_out` | `skipped_no_number`), `sent_at` (nullable), `failure_reason` (nullable Text), `whatsapp_message_id` (nullable — captured for future delivery-status reconciliation; write-only today since no delivery-status webhook is wired up yet, see Open Questions).
- `campaigns/domain/audience.py`: `AudienceFilter` — deliberately **not** the full Customer Segmentation Engine (a separate, not-yet-built P1 roadmap ticket this plan doesn't build). Shaped as a small typed union: `{"kind": "all"}` | `{"kind": "ordered_within_days", "days": int}` | `{"kind": "no_order_within_days", "days": int}`, resolved directly against `Order`/`Customer` via a repository query — plus an unused `segment_id: str | None` field on the stored JSON, an explicit extension point for the Segmentation Engine ticket to populate later without a migration. This is a real scope cut from what the roadmap ticket's "target segment" phrasing implies, stated here rather than silently narrowed — see Assumptions.
- `campaigns/domain/tier_enforcement.py`: `remaining_quota_today(waba, sent_today_count: int) -> int`. `sent_today_count` comes from a `CampaignRecipientRepository` query counting `status == "sent"` rows with `sent_at` inside the merchant's current local calendar day, using `Merchant.timezone` — reusing the same per-merchant timezone field `shared/scheduler.py`'s `send_due_appointment_reminders` already established, rather than assuming UTC midnight (an approximation of Meta's actual daily-window semantics, flagged in Open Questions since Meta doesn't publicly document whether its own reset is calendar-day-in-some-timezone or a rolling 24h window).
- **Overflow policy — queued to the next tick, never dropped.** Justified against the roadmap ticket's own status model: there's no `partially_sent` status, and a merchant who scheduled a campaign to 500 customers but is tier-capped at 250/day would see either "completed" (a lie — half never got sent) or a silent drop (violates the ticket's own "a merchant can view send progress and a basic delivery report" acceptance criterion) if overflow recipients were discarded. Instead: capped-out `CampaignRecipient` rows stay `pending`, `Campaign.status` stays `sending` (not `completed`) until every recipient row reaches a terminal status, and the next day's ticks simply keep draining `pending` rows — no cursor or explicit "day 2 resume" bookkeeping needed, since the query is always "whatever's still pending."
- `campaigns/domain/send_orchestrator.py`: `send_campaign_batch(session, tenant, campaign, waba, sender, quota_remaining) -> int`. Resolves the audience via `audience.py` (excluding `Customer.marketing_opt_out=True`, per Phase 12, and defensively skipping any customer with no `whatsapp_number` — can't happen today since it's the identity key, kept as a `skipped_no_number` outcome anyway for schema-level defensiveness), materializes `CampaignRecipient` rows on first run, then sends up to `min(quota_remaining, _MAX_SENDS_PER_TICK)` pending rows via the exact same `WhatsAppSender.send_template_message` method `notifications/adapters/whatsapp_channel.py`'s appointment-reminder path already calls — the literal reuse of `conversation/adapters/whatsapp_client.py`'s send path the roadmap ticket asks for. Each outcome updates its `CampaignRecipient` row; a failed send is logged and recorded `failed`, never raised, matching the existing best-effort outbound-send convention everywhere else in this codebase.
- `campaigns/domain/campaign_service.py`: `create_campaign(session, tenant, *, name, template_id, audience_filter, scheduled_at, created_by) -> Campaign` — the same-process domain function future Phase-2 tickets (Automated Reorder Reminders, Lost Customer Win-back) will call directly rather than looping back through the dashboard HTTP API, matching this codebase's existing convention of cross-module calls happening as plain function calls within one deployed process (`TECH_STACK.md`'s "modular by domain... communicating through interfaces... deploy as one process").
- Rate-limiting beyond the daily cap (the ticket's own "avoid tripping Meta's per-number throughput limits" criterion): a fixed `_MAX_SENDS_PER_TICK = 50` batch size, throttled by the scheduler's existing 5-minute tick interval rather than a token-bucket or explicit delay — so a large campaign fans out over several ticks by construction, not just capped by the daily ceiling. The exact number is a placeholder tuned to no live-volume data (flagged in Open Questions).
- `campaigns/adapters/repository.py`: `CampaignRepository`, `CampaignRecipientRepository` (tenant-scoped CRUD, the per-day sent-count query, the pending-rows-to-send query).
- `campaigns/api/router.py`: `POST /api/v1/campaigns` (create, `status=draft`), `PUT /api/v1/campaigns/{id}` (edit while `draft` only), `POST /api/v1/campaigns/{id}/schedule` (`draft → scheduled`, template must be `meta_approval_status="approved"` or this 422s — checked at schedule time, not just creation time, since approval can lag template submission), `POST /api/v1/campaigns/{id}/cancel` (`scheduled`/`sending → failed`; a merchant-cancel is recorded via the same `failed` status the ticket's model offers, distinguished by leaving already-`sent` `CampaignRecipient` rows untouched — see Assumptions on the missing dedicated `cancelled` state), `GET /api/v1/campaigns` (list), `GET /api/v1/campaigns/{id}` (detail, includes recipient counts grouped by status — the "basic delivery report" the ticket asks for).
- `identity/api/router.py` (or a new `onboarding` settings endpoint, mirroring `PUT /api/v1/onboarding/whatsapp`'s existing shape): `PUT /api/v1/onboarding/whatsapp/messaging-tier` — updates `WhatsAppBusinessAccount.messaging_tier_daily_limit`.
- `shared/scheduler.py`: `send_due_campaigns()`, registered at the same 5-minute interval as the two existing jobs — queries `Campaign` rows where `status == "scheduled" AND (scheduled_at IS NULL OR scheduled_at <= now)`, transitions them to `sending`, plus any already-`sending` campaign (resuming overflow from a prior tick/day); for each, resolves `remaining_quota_today` and calls `send_campaign_batch`; marks `completed` (sets `completed_at`) once every recipient row is terminal. Mirrors the abandoned-order sweep's "query due work, act, commit, log a count" shape exactly, including an injectable `now_utc` parameter for the same day-boundary testability convention `send_due_appointment_reminders` already established.
- Tests: `AudienceFilter` resolution for all three kinds against seeded `Order`/`Customer` fixtures; tier-ceiling enforcement (a merchant capped at a small limit sends exactly that many today, the rest stay `pending`, none over); opted-out customers are skipped and recorded `skipped_opted_out`, never sent to; scheduling against a non-`approved` template 422s; a simulated day-boundary (injectable `now_utc`, mirroring `send_due_appointment_reminders`'s own test convention) resumes overflow without re-sending already-`sent` rows; cancel mid-run stops further sends but leaves prior `sent` rows intact; `create_campaign()` callable directly (not just through the router) with a `created_by="system:test"` sentinel, proving the future-job interface point works.

**Frontend**: none in this phase — deferred to Phase 15 by design (mirrors `IMPLEMENTATION_PLAN.md` Phase 7 Notifications' precedent of a backend-only phase, and matches this plan's own explicit phase sequencing).

**Definition of done**: curl-create a campaign against an approved template with `{"kind": "all"}` audience, `POST .../schedule` with no `scheduled_at`; manually invoke (or wait one tick for) `send_due_campaigns`; `CampaignRecipient` rows flip to `sent` up to the WABA's tier ceiling and `GET /api/v1/campaigns/{id}` reports accurate `sent`/`pending`/`skipped_opted_out` counts; re-run against a seeded 2-recipient tier cap with 5 target customers to demonstrate the overflow-to-next-tick behavior (via injected `now_utc` a day later, the remaining 3 send and the campaign reaches `completed`); a customer seeded with `marketing_opt_out=True` in the audience is skipped and shows as `skipped_opted_out` in the report, never receiving a send.

## Phase 15 — Dashboard campaign UI

Wires the roadmap ticket's UI acceptance criteria ("a merchant can view send progress and a basic delivery report from the dashboard") onto Phase 13/14's now-complete API surface. No new backend risk here — the one thing worth getting right is making the constraints Phase 13/14 enforce server-side (only `approved` templates are schedulable, opted-out customers are silently excluded) legible in the UI *before* a merchant hits a 422, not just as an error toast after the fact.

**Frontend**
- `frontend/src/features/campaigns/useCampaigns.ts`: list/detail/create/schedule/cancel hooks; the detail query uses `refetchInterval` while `status` is `scheduled`/`sending`, mirroring `useOrders.ts`'s existing cache-and-revalidate convention for "visible progress within seconds" — same rationale, applied to campaign send progress instead of order status.
- `CampaignsPage.tsx`: table of campaigns (name, status badge, audience-size estimate, sent/pending counts); "New campaign" opens the create flow.
- `CampaignForm.tsx`: name input; template picker (only `approved` templates are selectable — `pending`/`rejected`/`paused` templates are shown but disabled with a tooltip explaining why, sourced from `useTemplates.ts` built in Phase 13); audience-filter selector (All customers / Ordered in the last N days / No order in the last N days — the three `AudienceFilter` kinds Phase 14 built, radio-style with a numeric input for the day count on the latter two); schedule picker (Send now / pick a date-time, RHF + Zod per the existing form convention).
- `CampaignDetailPage.tsx`: recipient counts broken out by status (sent/pending/failed/skipped_opted_out), a Cancel button shown only while `scheduled`/`sending`.
- `Layout.tsx`: a "Campaigns" nav entry (Templates + Campaigns), shown unconditionally — same ungated placement Phase 13's Templates page uses.
- Tests: the template picker disables non-approved templates and shows the tooltip reason; each audience-filter selection maps to the correct `AudienceFilter` payload shape; status badges and recipient counts render correctly from a mocked detail response; the Cancel button only renders for cancellable statuses.

**Backend**: none — pure frontend phase, matching this plan's explicit "campaign entity/send engine → dashboard campaign UI" sequencing.

**Definition of done**: log in, create a campaign end-to-end from the dashboard (pick an approved template, choose "no order in 30 days," schedule for now), watch it move Scheduled → Sending → Completed (or stay Sending with a visible tier-capped count if the seeded WABA's daily limit is small) with live recipient counts updating via polling and no page reload; cancel a still-scheduled campaign and confirm `GET /api/v1/campaigns/{id}` shows zero sends occurred.

## Phase 16 — Video & document template headers

Deliberately deferred and deliberately small. Phase 1 of this feature (Phases 12-15 above) is text-only and single-image-header templates only, per the settled scope decision. This phase is sequenced last because it's additive to Phase 13's media-upload adapter, not new plumbing: Meta's Resumable Upload API → media ID → template HEADER component is the exact mechanism `campaigns/adapters/media_upload.py`'s `upload_header_image` already implements; this phase widens its type coverage rather than building a second upload path.

**Backend**
- `campaigns/domain/models.py`: `MessageTemplate.header_type` enum widened from `NONE | TEXT | IMAGE` to include `VIDEO | DOCUMENT`.
- `campaigns/adapters/media_upload.py`: `upload_header_image` generalizes to `upload_header_media(kind: Literal["image", "video", "document"], data: bytes, content_type: str) -> str` — the Resumable Upload call itself doesn't change per kind (Meta's upload API is media-type-agnostic at that layer, exactly as flagged as the extension point in Phase 13); only a per-kind `_MAX_SIZE_BYTES` / `_ALLOWED_CONTENT_TYPES` lookup changes (video ≤16MB, `video/mp4`/`video/3gpp`; document ≤100MB, `application/pdf`, per Meta's documented template-header limits).
- `campaigns/domain/template_validation.py`: header validation extended to check size/MIME per kind; a `DOCUMENT` header additionally requires a display filename (Meta's spec requirement), stored as `MessageTemplate.header_filename` (new nullable column, small migration).
- Tests: size/MIME validation per kind (including rejection cases); `MetaTemplateGateway` payload-shape test for a `VIDEO`/`DOCUMENT` header template, confirming the HEADER component's `example.header_handle` wiring is identical to the Phase 13 image path.

**Frontend**
- `TemplateForm.tsx`: header-type select gains Video/Document options; the file-input `accept` attribute narrows per kind; a document header adds the required display-filename field.

**Definition of done**: create and submit a VIDEO-header MARKETING template from the dashboard; the Meta gateway payload and returned `meta_template_id` round-trip the same way the Phase 13 image-header path did, confirming the extension point added no new plumbing — only a wider validation table and an extra form field.

## Assumptions made in absence of a proposal doc

- **Audience targeting is a lightweight inline `AudienceFilter` (all / ordered-within-N-days / no-order-within-N-days), not the full Customer Segmentation Engine.** The roadmap ticket's "target segment" language leans on that separate, not-yet-scheduled P1 ticket; building it wasn't in scope here, so this plan ships a minimal substitute with an explicit `segment_id` extension point for that ticket to populate later.
- **Messaging tier lives on `WhatsAppBusinessAccount`, not `Merchant` or a new table**, reasoned from Meta assigning tiers per phone number — a real dependency-driven call, not an arbitrary one, but still a call a proposal doc would normally make explicit rather than leaving to be inferred from Meta's own model.
- **Tier-ceiling overflow is queued to the next scheduler tick/day, never dropped**, chosen to keep `Campaign.status`'s five-value enum honest (no silent data loss under `completed`). A proposal doc might instead have wanted a dedicated `partially_sent` status, or a merchant-facing choice between "queue the rest" and "drop the rest."
- **`Campaign.status` has no dedicated `cancelled` value** — cancelling maps onto the ticket's own `failed` state, distinguished only by which `CampaignRecipient` rows are `sent` vs `pending` at cancel time, not by a separate status. A proposal doc might want `cancelled` distinguished from a genuine send failure for reporting purposes.
- **`CampaignRecipient.status`'s five values (`pending`/`sent`/`failed`/`skipped_opted_out`/`skipped_no_number`) are this plan's own design**, not specified anywhere in the roadmap ticket.
- **No retry/backoff for `failed` recipient rows** — matches `ARCHITECTURE.md` §10's existing "no retry/backoff sophistication for outbound WhatsApp notification sends beyond try, log failure" rule, applied here too rather than inventing new sophistication for campaigns specifically. A merchant would need to create a fresh campaign to re-target failed recipients.
- **Per-tick send-rate limiting is a placeholder constant (`_MAX_SENDS_PER_TICK = 50`, on the existing 5-minute scheduler cadence)**, not derived from any documented Meta throughput number (none is consistently published) — tunable, not load-tested against a live WABA at volume.
- **Template body variables carry only minimal per-recipient context (customer name, business name) for v1** — no richer personalization (last order items, an offer amount) is built, since a broadcast campaign isn't tied to a single order the way lifecycle notifications are.
- **Campaign analytics beyond a basic sent/pending/failed/skipped count (Phase 15's "delivery report") is explicitly deferred**, not built here — attribution, revenue-per-campaign, and re-engagement rate belong to `docs/product-roadmap.md`'s Phase 4 "Revenue & Retention Analytics Dashboard" ticket, which this plan doesn't duplicate.
- **Template editing after Meta submission is not supported** — Meta itself requires delete-and-recreate to change an approved template's content, so `PUT /campaigns/templates/{id}` only works pre-submission; the UI's only post-submission action is delete.
- **The Campaigns/Templates nav section is ungated by vertical** (shown to every merchant regardless of `restaurant_enabled`/`appointment_enabled`), unlike Catalog/Services — a proposal doc might instead have wanted campaigns gated behind a plan/tier flag not built anywhere in this codebase today.
- **No new permission gate beyond existing staff auth** — this codebase has no multi-user roles (per the original brief's explicit exclusion, still true), so campaign creation/sending is available to any authenticated `StaffUser`, same as every other dashboard action.

## Open questions

- Meta's exact daily-tier reset window semantics (rolling 24h vs. a calendar day, and in which timezone) aren't fully documented publicly. This plan approximates with "merchant-local calendar day" (reusing `Merchant.timezone`), which may not match Meta's actual enforcement — needs verifying against a live WABA at real volume, the same kind of gap Phases 5-8 of the original MVP plan flagged for missing live credentials.
- Whether Meta's real per-number throughput/burst limits (distinct from the daily tier cap) require a smaller or larger per-tick batch than the `_MAX_SENDS_PER_TICK = 50` this plan assumes — no single documented number exists; needs live testing once real send volume exists.
- Whether a rejected template should proactively notify the merchant (a WhatsApp/dashboard alert) or stay passively visible on the Templates page only — this plan ships the passive version; not specified by the roadmap ticket either way.
- Whether the future Automated Reorder Reminder / Lost Customer Win-back jobs should own their own audience-computation logic or reuse this phase's `AudienceFilter` types via `create_campaign()` — this plan exposes the function as the interface point but doesn't resolve which of those (not-yet-built) tickets should shape that call.
- Whether opt-out (Phase 12) should also suppress future reminder-style jobs (reorder reminders, appointment reminders) that Meta might classify as UTILITY rather than MARKETING category — Meta's own category boundary here isn't unambiguous from documentation alone, and this plan only wires the opt-out flag into Phase 14's campaign send path, not into `shared/scheduler.py`'s existing appointment-reminder job.
- Whether `CampaignRecipient.whatsapp_message_id` should eventually feed a delivery-status webhook (Meta's `messages` status callbacks — sent/delivered/read/failed — which this codebase's webhook handler doesn't currently parse for outbound message IDs at all) to make "delivered" a real recipient status rather than "the send call succeeded" — left for a future ticket, since it touches the webhook parsing this plan otherwise leaves untouched for message-level events.
