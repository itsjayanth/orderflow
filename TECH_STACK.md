# Orderflow — Tech Stack (MVP)

Concrete stack decisions for the design in `ARCHITECTURE.md`. Backend constraints (Python, PostgreSQL, SQLAlchemy, Alembic) were given; everything else below is chosen to fit the patterns `ARCHITECTURE.md` already commits to (hexagonal/ports-adapters, repository, strategy, cache-and-revalidate, wizard-driven onboarding) rather than picked independently.

## Summary

| Layer | Choice |
|---|---|
| Backend language/runtime | Python 3.12+ |
| Web framework | FastAPI |
| ORM | SQLAlchemy 2.0 (typed, async) |
| Migrations | Alembic |
| Database | PostgreSQL |
| Validation / schemas | Pydantic v2 |
| Background jobs / scheduling | APScheduler (in-process worker) |
| Auth | JWT access + refresh tokens, Argon2 password hashing |
| Secrets encryption (WhatsApp token, etc.) | `cryptography` (Fernet) at the application layer |
| Payments SDK | official `razorpay` Python SDK |
| WhatsApp integration | direct Graph/Cloud API calls via `httpx`, wrapped in our own adapter |
| Backend package/dep manager | `uv` |
| Backend lint/format/type-check | Ruff + mypy |
| Backend testing | pytest, pytest-asyncio, httpx `AsyncClient` |
| Frontend framework | React 18 + TypeScript |
| Frontend build tool | Vite |
| Server-state / data fetching | TanStack Query |
| Client-only state (rare) | Zustand |
| Routing | React Router |
| UI components / design system | Tailwind CSS + shadcn/ui (Radix primitives) |
| Forms / validation | React Hook Form + Zod |
| API typing bridge | types generated from FastAPI's OpenAPI schema (`openapi-typescript`) |
| Frontend lint/format/type-check | Biome + `tsc` |
| Frontend testing | Vitest + React Testing Library |

## Backend

**FastAPI**, not Django/Flask. Reasoning: the system is I/O-bound around webhooks (WhatsApp, Razorpay) and a polling dashboard — FastAPI's native async fits that directly; its Pydantic-based request/response models double as the typed contract the frontend generates types from; and its automatic OpenAPI schema is what makes the frontend's typed API client possible without hand-maintained duplication. Django's batteries (admin, ORM) aren't a fit since SQLAlchemy/Alembic were already specified.

**Deployment topology: single FastAPI application, modular by domain — not microservices.** `ARCHITECTURE.md` Section 3 lists components (Identity & Access, Onboarding, Conversation Handler, Ordering Flow UI, Catalog, Customer, Order, Payment, Notification, Dashboard API) as *logical* modules with clear ownership boundaries; at pilot scale (1-2 restaurants) they deploy as one process, organized as separate Python packages/modules communicating through the interfaces the hexagonal architecture already defines. Splitting into real microservices is a scaling decision for later, not an MVP one — and because the ports/adapters boundaries are already in the code, that split stays possible without a rewrite.

**Data layer conventions:**
- Primary keys: UUID (v4) on every table, not auto-increment integers — avoids leaking row counts/order across tenants and is the safer default for a multi-tenant schema (`ARCHITECTURE.md` Section 2).
- SQLAlchemy 2.0's typed declarative models (`Mapped[...]`) throughout — mypy can then actually check repository code.
- Alembic migrations are autogenerated then hand-reviewed before commit; one migration per PR that changes schema, never edited after merge.
- Every repository method takes a `TenantContext` (carries `merchant_id`) as the first argument — this is where the multi-tenancy enforcement from `ARCHITECTURE.md` Section 2 actually lives in code, not just in the doc.

**Background jobs: APScheduler**, not Celery+Redis, for MVP. The only recurring jobs at this scale are the payment-reconciliation poll and the abandoned-order timeout sweep (`ARCHITECTURE.md` Sections 3d/8) — both low-frequency, low-volume. APScheduler running inside a small worker process covers this without standing up Redis + Celery workers. If notification volume or task fan-out grows past what a pilot needs, Celery+Redis is the natural upgrade — treat it as a seam, the same way Phase 2 POS sync is a seam, not something to build preemptively.

**WhatsApp integration: raw `httpx` calls against the Graph/Cloud API, wrapped in our own `WhatsAppAdapter`**, rather than a third-party WhatsApp Python package. This keeps the `NotificationChannel`/`OrderingSurface` ports (`ARCHITECTURE.md` Section 4) implemented against Meta's actual API surface instead of a smaller community library's abstractions and release cadence — important since WhatsApp Flows (the ordering "mini UI") and template-message policy are core to the product, not incidental. (Libraries like `pywa` exist and support Flows — worth a spike if they meaningfully cut implementation time, but the adapter boundary means swapping to one later is contained.)

**Auth: JWT (access + refresh), Argon2 for password hashing.** Access tokens short-lived, refresh tokens rotated; frontend stores the access token in memory and the refresh token in an httpOnly cookie (not `localStorage`, to limit XSS blast radius). Argon2 (via `argon2-cffi`) over bcrypt — it's the current recommended default for new systems.

**Secrets at rest:** `WhatsAppBusinessAccount.access_token_encrypted` (and any other stored provider secret) is encrypted at the application layer with `cryptography`'s Fernet, keyed from an environment-provided secret — not stored or logged in plaintext anywhere. If/when deployed to a cloud provider with a KMS, migrate the key source to that KMS; the encryption call site doesn't change.

**Tooling:** `uv` for dependency/env management (fast, single `pyproject.toml`, increasingly the default choice for new Python projects). Ruff for linting *and* formatting (one fast tool, replaces flake8+isort+black). mypy for type-checking, run in CI against the SQLAlchemy 2.0 typed models. pytest + pytest-asyncio for tests; FastAPI's `TestClient`/`httpx.AsyncClient` for endpoint tests; a real Postgres (via `testcontainers` or a docker-compose test DB) for repository/integration tests rather than mocking the database, so tenant-scoping and migration behavior are verified against the real engine, not an approximation of it.

## Frontend (Merchant Dashboard UI)

**React 18 + TypeScript on Vite.** Standard, fast dev loop, largest ecosystem for the component libraries below — no reason to deviate for a dashboard-shaped app.

**TanStack Query for all server state.** This is the concrete implementation of the "cache-and-revalidate data-fetching" pattern `ARCHITECTURE.md` Section 4 already specifies for the orders list — short-interval `refetchInterval` polling gets the dashboard to "order visible within seconds" without websocket infrastructure, plus built-in retry/stale-while-revalidate behavior for free. Local/client-only UI state (onboarding wizard's current step *before* it's persisted, cart preview state) uses Zustand only where it's genuinely not server state — most state in this app *is* server state, so Zustand's footprint should stay small.

**Tailwind CSS + shadcn/ui.** shadcn/ui ships Radix-based, accessible component primitives you own the source of (not an opaque npm dependency) — a good fit for "shared component/design system across onboarding wizard and dashboard" (`ARCHITECTURE.md` Section 4), since components can be customized in place rather than fighting a packaged library's theming API.

**React Hook Form + Zod.** Onboarding steps and catalog/menu forms are the forms-heaviest part of this app; Zod schemas validate client-side and pair naturally with the OpenAPI-generated types from the backend (Section below) so validation rules don't silently drift from what the API actually accepts.

**Typed API client generated from FastAPI's OpenAPI schema** (`openapi-typescript` or similar), regenerated as part of the build/CI. This is a direct, enforced link between backend Pydantic models and frontend types — a schema change that breaks the frontend fails typecheck instead of failing silently at runtime.

**Biome + `tsc`** for lint/format/type-check — mirrors the backend's "one fast consolidated tool" choice (Ruff), single config instead of ESLint+Prettier's two-tool setup.

**Testing: Vitest + React Testing Library**, focused on the container/presentational split (`ARCHITECTURE.md` Section 4) — presentational components get straightforward render tests, containers get tested against a mocked TanStack Query client.

**Customer-facing "Ordering Flow UI":** for the MVP, this is WhatsApp Flow JSON (declarative screens, defined per `ARCHITECTURE.md` Section 6) plus a FastAPI endpoint implementing the Flow data-exchange protocol — **no separate frontend framework needed**, since WhatsApp renders the UI natively. If the fallback webview strategy (Section 6's `OrderingSurface` alternative) is ever needed, it would reuse this same React/Vite toolchain rather than introducing a second one.

## Repo layout (proposed)

```
orderflow/
├── ARCHITECTURE.md
├── TECH_STACK.md
├── CLAUDE.md
├── README.md
├── docs/
│   └── project-brief.txt
├── backend/
│   ├── pyproject.toml
│   ├── alembic/
│   └── src/
│       ├── identity/          # Identity & Access Service
│       ├── onboarding/        # Onboarding Service
│       ├── conversation/      # WhatsApp Conversation Handler
│       ├── ordering_flow/     # Ordering Flow UI backend (Flow data-exchange)
│       ├── catalog/           # Catalog Service
│       ├── customers/         # Customer Service (Customer + Address)
│       ├── orders/            # Order Service (both state machines)
│       ├── payments/          # Payment Service
│       ├── notifications/     # Notification Service
│       ├── dashboard_api/     # Merchant Dashboard API (composes the above)
│       └── shared/            # ports/interfaces, TenantContext, db session, encryption
└── frontend/
    ├── package.json
    └── src/
        ├── features/
        │   ├── onboarding/
        │   ├── orders/
        │   ├── catalog/
        │   └── customers/
        └── shared/             # design system components, API client, hooks
```

Each `backend/src/<module>/` follows the same internal shape (hexagonal): `domain/` (entities, state machines, port interfaces), `adapters/` (SQLAlchemy repositories, external API clients), `api/` (FastAPI routers). This is what keeps `orders/` swappable behind `PaymentGateway`/`NotificationChannel` interfaces without reaching into `payments/` or `notifications/` internals.
